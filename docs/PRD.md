# PRD — Product Requirements Document

> Статус: v0.2 (2026-11-16). Идея зафиксирована по коду и текущей задаче: внутренний LLM-ассистент по корпоративной базе знаний. Если продукт задумывался иначе — поправить этот файл, остальные документы ссылаются на него.

## Проблема и цель

Сотрудники тратят время на поиск ответов в регламентах, приказах и вики (отпуска, командировки, доступы, продукт, поддержка). Знание размазано по документам и уходит вместе с людьми. Цель — один чат, который отвечает по актуальным внутренним документам, показывает источники и честно говорит «в базе нет ответа».

## Пользователи

- Сотрудники компании — задают вопросы в чате (пилот на синтетической базе).
- HR, ИТ, финансы — владельцы документов, по которым отвечает ассистент.
- (Позже) администратор базы знаний — загружает и обновляет документы.

## Функциональные требования

### Must (без этого продукта нет)

- Чат с сохранением истории диалога (`POST /chat`, `conversation_id`).
- Ответы опираются на корпоративную базу знаний (RAG), в ответе — источники.
- Если в базе нет ответа — ассистент говорит об этом и не выдумывает.
- Архивные/недействующие документы не используются как действующие правила.
- Стриминг ответа (`POST /chat/stream`, SSE).

### Should (важно, но можно отложить)

- Eval-набор вопросов/эталонов и регулярные прогоны (следующий шаг).
- Ограничение истории по токенам с учётом system-промпта RAG.
- Переформулировка follow-up вопросов для поиска (query rewriting).

### Could (хотелки на будущее)

- Hybrid search (BM25 + vector) и rerank.
- Загрузка/обновление документов через API и фоновая переиндексация.
- Разграничение доступа к документам по отделам (RBAC).
- Фронтенд с парсером SSE.

## Не-требования (сознательно НЕ делаем)

- Eval-функции в этом шаге — только корпус и рабочий RAG; сами прогоны делаются следующим шагом.
- Авторизация и мультитенантность.
- Векторная БД как отдельный сервис — используем pgvector в текущем Postgres.
- Полный LangChain/LangGraph-стек в runtime.

## Метрики успеха

- Точность ответов на eval-наборе: совпадение факта/числа/срока с эталоном.
- Retrieval: hit@k (нужный документ в топ-k) и MRR.
- Доля ответов с корректно указанным источником.
- Доля корректных отказов на вопросы вне базы.
- Латентность ответа (p95) и стоимость запроса.
